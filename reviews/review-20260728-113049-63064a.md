## High Severity

### 1. Untrusted workspace HTML is opened directly as a local file

- File path and line number: `mcp/src/index.ts:838`
- Severity: high
- Category: Diff
- Description: `vnsh_workspace_open` writes decrypted workspace HTML directly to a temporary `.html` file and opens it in the browser. Workspace content is untrusted and may contain scripts. Running it as `file://` bypasses the Worker viewer's sandbox and CSP protections and can allow network exfiltration or local-file-origin abuse depending on browser behavior.
- Suggested fix: Open untrusted HTML through a generated sandbox wrapper, using an iframe without `allow-same-origin` plus a restrictive CSP, or route users to the hardened `/w/:id#w=...` web viewer. Add tests asserting `workspace_open` does not directly execute raw HTML.

### 2. Workspace create path trusts caller-controlled body size

- File path and line number: `worker/src/index.ts:499`
- Severity: high
- Category: Diff
- Description: `POST /api/workspace` enforces `MAX_BLOB_SIZE` only from the caller-controlled `Content-Length` header, then streams `request.body` directly to R2. A client can omit or understate `Content-Length` and store content above the intended 25 MB limit, creating storage/cost and resource-exhaustion risk.
- Suggested fix: Enforce size while reading or streaming the body, or use a Worker-side bounded stream that aborts after `MAX_BLOB_SIZE`. Add regression tests for missing and misleading `Content-Length`.

### 3. Workspace update path has the same body-size bypass

- File path and line number: `worker/src/index.ts:604`
- Severity: high
- Category: Diff
- Description: `PUT /api/workspace/:id` has the same body-size bypass as create: it trusts `Content-Length` before streaming the replacement body to R2. An authenticated writer can upload oversized workspace revisions despite the 25 MB limit.
- Suggested fix: Apply the same server-side byte limit during PUT body consumption, and cover both create and update paths with oversized streaming-body tests.

### 4. Worker implementation is a god file

- File path and line number: `worker/src/index.ts`
- Severity: high
- Category: Holistic
- Description: The worker is a 4,900+ line file mixing request routing, storage logic, workspace APIs, analytics, install scripts, static HTML/CSS/JS, blog pages, and scheduled cleanup. This makes agent-driven changes risky because unrelated concerns share one large edit surface.
- Suggested fix: Split the worker into focused modules such as `routes/`, `storage/`, `analytics/`, `pages/`, `scripts/`, and `workspace/`, with static HTML/templates moved out of the main handler.

### 5. Storage architecture documentation is stale

- File path and line number: `README.md`, `docs/architecture.md`, `docs/self-hosting.md`, `docs/operations.md`
- Severity: high
- Category: Holistic
- Description: Documentation is materially stale around storage architecture. Several docs still instruct users to create or bind `VNSH_META` KV, while `worker/wrangler.toml` and `CLAUDE.md` say KV is deprecated and R2 custom metadata is the source of truth.
- Suggested fix: Update operational, self-hosting, and architecture docs to the current R2-only design, remove KV setup steps, and add a migration note for older deployments.

### 9. Crypto and URL parsing logic is duplicated across clients

- Severity: medium
- Category: Holistic
- Description: Crypto and URL parsing logic is duplicated across multiple packages and inline browser code. This is a high-risk area for drift because v1/v2 URL support, key validation, and encoding rules must remain byte-compatible.
